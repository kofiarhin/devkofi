# DevKofi Tickets

Tickets define **what should change and why**.

One ticket equals one outcome, one visible finish line, and one reviewable change. Each ticket should reference the relevant roadmap/request and capture:

- problem and user outcome;
- current repository evidence;
- desired behavior;
- scope and explicit exclusions;
- functional requirements;
- acceptance criteria;
- confirmed constraints/dependencies;
- unresolved material questions.

Do not turn tickets into implementation designs. Technical solution details belong in `spec/`.

Use stable zero-padded filenames when no stronger project convention exists, for example `001-join-mentorship-validation.md`.
